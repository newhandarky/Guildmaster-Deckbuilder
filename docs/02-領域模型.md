# 領域模型

本模型以完整遊戲為目標：基礎版、第一擴充、後續 Content Pack、AI 與線上對戰共用同一套純規則核心。MVP 只啟用基礎 Rules Module，不使用另一套簡化 state。

## 1. 設計目標

- 規則狀態與 React／網路／儲存完全分離。
- 所有隨機結果可用 seed 與 RNG state 重現。
- 每張卡牌實例有唯一 instance ID；同名卡仍可分別追蹤。
- 卡片定義唯讀；所在區域、配戴關係、血量與暫時效果屬於對局狀態。
- 所有合法變更都經由 Command，輸出新 state、Events 與 Pending Choice。
- 完整 `GameState` 是權威狀態；UI 與 AI 只取得依 viewer 裁切的 `PlayerView`。
- 基礎版與擴充都以 `ContentPack` + `RulesModule` 組合；engine 不 hard-code pack 名稱。
- 規則身份與呈現身份分離：`CardDefinition.id` 是唯一規則 key；人物名稱、圖片與 UI 文案不進規則 state。
- Snapshot、Command、Event 與 Replay 都帶版本與內容 manifest。

## 2. `GameState`

| 欄位 | 用途 |
| --- | --- |
| `schemaVersion` | Snapshot schema migration 版本 |
| `engineVersion` / `rulesetVersion` | 引擎與規則相容版本 |
| `contentPacks` | pack ID、版本與內容 hash |
| `rulesModules` | 啟用的 module ID、版本與設定 |
| `gameId` / `seed` / `rngState` | 對局識別與可重現亂數 |
| `revision` | 每個成功 Command 後遞增 |
| `status` | setup、playing、finalRound、finished 等 lifecycle |
| `players` | 依座位順序排列的玩家狀態 |
| `activePlayerId` / `startingPlayerId` | 目前行動者與輪次邊界 |
| `round` / `turn` / `phase` | 回合狀態；中文顯示「討伐階段」，enum 可保留 `combat` |
| `sharedZones` | 酒館與 Rules Module 建立的公共區域 |
| `enemyEncounters` | 同時存在的魔王、魔物、究極魔神與部位 |
| `removedCards` | 本局移除區 |
| `moduleState` | 各 Rules Module 自己的可序列化狀態 |
| `effectState` | pending choice、counter consent、lifecycle、command 與 post-command pipeline 的可序列化 continuation |
| `endState` | 已觸發的結束條件、觸發 revision 與輪次邊界 |
| `eventLogCursor` | Replay／同步用事件位置；不把函式存入 state |

`GameState` 不應新增 `vol1Something` 之類的頂層欄位。擴充專屬狀態放在 namespaced `moduleState[moduleId]`，由對應 schema 驗證。

### Effect execution state

`effectState.pendingChoice` 是版本化、可序列化的暫停點，保存 execution ID、choice ID、允許 actor、選項、後續 effects 與純資料 context；不保存 closure、UI 文案、圖片或顯示名稱。選擇只能以帶 `expectedRevision` 的 `RESOLVE_EFFECT_CHOICE` Command 恢復，讓 Snapshot／Replay 在相同 RNG 與 command 下重現。

`effectState.pendingCounterConsent` 是獨立於單 actor choice 的多 actor 暫停點。Rules Module 以 JSON-only `CounterConsentPolicy` 宣告 counter resource、counter-owner requester、全體其他玩家 consent 與 deterministic explicit-command expiration authority；Effect AST 保存 request ID、四種 terminal outcome、已接受／尚需回覆 actors、registry 指紋與後續 cursor。`RESPOND_COUNTER_CONSENT`、`CANCEL_COUNTER_CONSENT`、`EXPIRE_COUNTER_CONSENT` 都驗證 actor、gameId、revision、requestId；pending 期間其他 command 不可繞過。accepted 將 `allPlayersByConsent` counter 權威地改為 public，declined／cancelled／expired 不揭露真值。

`effectState.pendingLifecycle` 另保存 lifecycle payload、Effect context、目前／剩餘 `{ moduleId, hookId }`、ruleset/module 版本指紋與 dispatch 起點的 rollback checkpoint。Snapshot round-trip 後，choice 完成會繼續同一 queue；未知 module、hook 或版本不符必須明確失敗。整次 lifecycle 是同一 transaction，後段 hook 失敗時不得留下前段 mutation。

`effectState.pendingCommand` 保存被 command-before choice 暫停的原始 `CommandEnvelope` 與尚未提交的 lifecycle events。choice 完成後只接續未完成 hook，再執行一次原 command，並進入與一般 command 相同的 post-command pipeline；失敗回到 command 起點。

`effectState.pendingPostCommand` 是 reducer 已成功、但 `event-before`、`event-after` 或 `command-after` choice 尚未完成時的 outer continuation。它以純 JSON 保存穩定 continuation ID、原 command envelope、command 起點 rollback checkpoint、一次固定的 reducer facts、尚未提交的 transaction events、`factIndex`、boundary／step cursor、lifecycle payload／context 與 registry 指紋。Snapshot restore 必須交叉驗證 pending choice、hook queue 與 outer cursor；checkpoint 不得遞迴包含任何 continuation。

原 command 到最後一個 post-command hook 是同一 transaction。choice 或 counter consent 暫停時 revision 與 `eventLogCursor` 不提交；恢復不重跑 reducer、不重建 facts、不重跑完成的 hooks，也不重新消耗 RNG。完整成功後 revision 只增加一次，event cursor 依最終事件數一次提交；任一後段錯誤皆以 outer checkpoint 回到 command 起點。hook-level `pendingLifecycle.rollbackState` 只負責單次 lifecycle dispatch，不能取代 outer checkpoint。

## 3. `PlayerState`

| 欄位 | 用途 |
| --- | --- |
| `id` / `seat` / `displayName` | 玩家識別 |
| `drawPile` / `hand` / `discardPile` | 個人牌庫、手牌、棄牌堆 |
| `party` | 有順序的 `PartySlot[]`；不寫死長度 5 |
| `playArea` | 已使用、等待休息棄置的道具等卡片 |
| `bonds` | 羈絆與完成狀態 |
| `turnResources` | 購買力來源、費用修正、已花費等暫時資源 |
| `counters` | HP 標記等可見／隱藏計數資源 |
| `moduleState` | 玩家層級、由 Rules Module 擁有的可序列化 state |
| `historyStats` | 擊敗魔王／魔物等不適合只靠目前區域回推的紀錄 |

### 3.1 `PartySlot`

- `adventurerInstanceId`
- `equipmentInstanceId?`
- 不另存位置；以陣列 index + 1 計算。
- 隊伍人數上限由 `getPartyLimit(state, playerId)` selector 根據 base 值、卡片效果與 Rules Module modifiers 計算。
- 基礎版 base 值為 5；這不是 engine constant。
- 上限下降時的超額處理由 Rules Module policy 決定。Vol.1 官方規則為從最右側開始，將冒險者與配戴裝備置入棄牌堆，直到符合上限。

### 3.2 `PlayerCounterState`

至少包含：

- `resourceId`：namespaced，例如 `vol1:ultimate-demon-hp`
- `amount`
- `visibility`：public、ownerOnly、allPlayersByConsent 等 policy ID

`allPlayersByConsent` 的 counter 在 PlayerView 對非 owner 一律裁切；只有 generic consent transaction 得到全部 required actors 接受後才切換為 `public`。request／accept／decline／cancel／expire 都發出帶 policy、registry、actor sets、status 與 stable reason code 的 structured event；不使用 UI local toggle 或牆鐘資料。
- `sourceRefs`：可選的究極魔神／部位／事件來源

權威 state 保存真實數值；`PlayerView` 依 visibility policy 顯示數值、只顯示存在與否，或完全隱藏。

## 4. 區域模型

### 4.1 `ZoneState`

不要為每個擴充直接新增固定欄位。所有區域以穩定 `ZoneId` 與 discriminated union 建模：

- `orderedDeck`：有順序的牌庫
- `faceUpRow`：招募區、商店、魔物區
- `singleSlot`：只允許一張的公開位置
- `attachmentArea`：配戴／附屬關係
- `moduleArea`：經 Rules Module schema 定義的擴充專屬區域

基礎版酒館由冒險者牌庫／招募區、物資牌庫／商店、魔物牌庫／魔物區、魔王牌庫等 zones 組成。第一擴充可加入究極魔神戰場、HP 備用區等專屬 zone，而不修改 engine 頂層型別。

### 4.2 公共供應牌庫

- 供應牌庫的抽取、展示與耗盡行為與玩家個人牌庫分開建模。
- 冒險者／物資牌庫因實際補列抽取而變空時產生一次 `SUPPLY_DECK_DEPLETED`，包含 card category 與 Rules Module ownership；已空且沒有抽取時不重複產生。
- 魔物牌庫不進入耗盡分支；循環錨點在同一 transaction 回牌庫底並補列，使 committed 魔物區始終正好 3 張。
- 哪些冒險者／物資耗盡事件會造成擴充內容登場或沒有額外結果，由啟用的 Rules Module 決定；UI 不自行補救。

## 5. 敵方目標與 Encounter

不得只用單一 `activeBossId` 表示所有敵方目標。

### 5.1 `EnemyEncounterState`

- `encounterId`
- `kind`：魔王列、魔物列、究極魔神等
- `targetIds: EnemyTargetId[]`
- `status`
- `rulesModuleId?`
- `resolutionPolicy?`：版本化 Rules Module policy ref；未知 module/policy/version 或 registry mismatch 不可恢復
- `state`：由對應 schema 驗證的可序列化 encounter state

### 5.2 `EnemyTargetState`

- `targetId`
- `cardInstanceId`
- `parentEncounterId?`
- `partKey?`：究極魔神部位等穩定 key
- `status`：available、engaged、defeated、removed 等
- `health?`：current/max 或 token pool reference
- `attachments`
- `modifiers` / `activeAbilityIds`
- `moduleState`

一般魔王可以是一個 encounter 中的一個 target；公開魔物列可以同時有三個 targets；多部位究極魔神可以是一個 encounter 中同時存在四個獨立 targets。泛用 encounter runtime 以 JSON-only `EncounterResolutionPolicy` 及 Effect AST 的 create/attach/damage/defeat/remove/finish nodes 處理固定 target／attachment IDs、health、disposition 與 completion；`required-targets-defeated` 必須明確宣告 `all` 或 `any`。整體擊敗條件不由 `targetIds.length === 0` 猜測，terminal target 不會重複結算。

Encounter events 保存 policy、registry、target/evaluation ref，Snapshot 與 lifecycle/post-command continuation 會驗證這些資料；choice 暫停後從既有 AST cursor 恢復，不重跑先前的 damage、移動、completion 或 RNG。此能力沒有載入任何正式或 provisional 多部位魔王內容，亦不自行推導討伐獎勵、終局、下一階段或供應耗盡行為；基礎供應耗盡改由 Rules Module 套用 `01-基礎版核心規則.md` 記錄的核准專案 policy。

## 6. 卡牌定義、替換與實例

`DiceDefinition` 是 Rules Module 擁有的版本化 JSON-only 定義（module、stable dice ID、sides）；`roll-die` 只引用它並發出含 registry fingerprint 與 face 的 `DIE_ROLLED` event。骰子結果不是 UI state，choice 暫停後從既有 Effect AST cursor 恢復，不重新消耗 RNG。

`AttackResolutionPolicy` 是 Rules Module 擁有的版本化 JSON-only health-target 攻擊定義：以 target／encounter／counter 條件選擇固定 damage 與既有 `EncounterResolutionPolicy`，純 evaluator 同時固定 combat evaluation、實際消耗的隊伍前綴、health before／after、致命 outcome 與 registry fingerprint。`ATTACK_TARGET` query 與 dispatch 共用 evaluation；非致命只更新 health，致命才銜接既有 reward、choice／consent 與 lifecycle transaction。沒有 matching policy 的 health target 維持不可攻擊，且不推導任何官方 HP 或多部位時序。

### 6.1 `CardDefinition`

- `id`：namespaced 穩定 ID，例如 `base:adventurer/example`
- `packId` / `definitionVersion`
- `type`：adventurer、material、boss、monster、bond、helper、starter、ultimateDemonPart 等可擴充 enum
- `copies`
- `honor`、`cost`、`purchasePower?`、`tags`
- `effects`

`id` 是規則、效果、卡片實例、存檔、Replay、AI 與網路同步的唯一卡片識別。它必須是中性機制 ID，不得包含人物名稱、官方名稱、圖片檔名或顯示文案。`CardDefinition` 不保存角色名稱、圖片檔名、玩家文案或 asset key；引擎不得讀取這些資料。

玩家顯示使用「物資、魔物、協助者、討伐階段」等官方中文；內部 enum 可保留英文。

### 6.2 卡片替換

`ContentPack` 可提供 replacement declarations：

- `replacementDefinitionId`
- `replacesDefinitionId`
- 適用 pack/version 範圍
- replacement priority 或衝突錯誤

建立 `ContentRegistry` 時先解析替換，再建立實例。被替換定義不與新版同時進入同一內容集合；Snapshot／Replay 保存實際 registry hash。

### 6.3 `CardInstance`

- `instanceId`
- `definitionId`
- `ownerId?`
- `state`：卡牌自身可序列化 state

配戴與附屬關係由 zone／target／party state 關聯，不寫回唯讀 definition。

## 7. Content Pack 與 Rules Module

### 7.1 `ContentPack`

每個基礎／擴充包提供：

- `manifest`：pack ID、semantic version、相容 ruleset、相依／衝突 pack
- `definitions`
- `replacements`
- `rulesModules`
- `effectExtensions`

組合時驗證 ID 唯一、版本相容、dependencies、conflicts、replacement graph 與內容 hash，再建立唯讀 `ContentRegistry`。

### 7.1a `PresentationPack`

Presentation Pack（Appearance Pack）是獨立、可替換且不影響規則的顯示資料集合。它以 `CardDefinition.id` 對應 `PresentationEntry`，包含 `displayName`、`portraitAssetKey`、`shortDisplayText`、可選 `variant`／`theme`／`locale`。同一張規則卡可有多套人物名稱與圖片；切換 pack 不可改變 effects、數值、definition ID、合法 Command、AI 決策或對局結果。詳見 `20-呈現包規格.md`。

### 7.2 `RulesModule`

Rules Module 以具名 extension points 組合，不用散落的 `if (vol1Enabled)`：

- `moduleId` / `version`
- `stateSchema` / `createInitialState`
- `setupContributions`
- `zoneDefinitions`
- `commandHandlers` / `eventHandlers`
- `effectExtensions`
- `lifecycleHooks`：只含可序列化 hook metadata、activation 與 Effect AST
- `combatRules`：版本化 JSON conditions、modifier、restriction 與 replacement outcome
- `equipmentEligibilityRules`：版本化 JSON eligibility conditions 與 rejection reason code
- `teamOverflowPolicies`：版本化 JSON team capacity／overflow policy
- `supplyRowConfigurations`：版本化 JSON deck／公開列配對與 refill-to-target evaluation
- `supplyRowRefreshPolicies`：版本化 JSON 公開列 destination、order 與 optional refill policy

team overflow policy 可採 automatic 或 `player-choice`；後者以既有 pending choice／command continuation 保存固定候選與 policy fingerprint，Snapshot 恢復後不重跑 reducer。
- `partyLimitModifiers` / overflow policy
- `endConditions`
- `scoringRules` / ranking rules
- `visibilityPolicies`
- `snapshotMigrations`

module state 必須是 JSON 可序列化資料；lifecycle hook、combat rule、combat reward policy 與 equipment eligibility rule 不得持有 closure 或直接寫入 `GameState`，所有變更只由 engine 解讀版本化資料後產生。CombatRewardPolicy choice continuation 保存固定 evaluation、policy cursor、Effect context 與 rollback checkpoint，可跨 Snapshot 恢復且不重跑 reducer、policy、events 或 RNG；未載入任何正式或 provisional 獎勵 policy。

泛用 continuous runtime 現在以 JSON-only Rules Module rules 衍生可重播 modifier/restriction/capacity boundary；不直接累加 `GameState`，source 離開有效位置後失效，且未載入任何正式或 provisional 卡牌效果。

目前 reducer 會為成功 command 與其產生的 facts 發出 `command-before`、`event-before`、`event-after`、`command-after` boundary；所有 boundary 均可透過可序列化 continuation 暫停，整批仍由 command transaction 保護。CombatRewardPolicy 可表達抽牌、暫時戰力／購買力與 counter 獎勵，但尚未掛接任何卡牌資料。

討伐合法性與 authoritative reducer 共用 `CombatEvaluation`。Rules Module 可用 `always`、phase、target kind、玩家 counter 與 all/any/not 組合條件，套用加減戰力 modifier、restriction reason code，以及 `defeat-target`／`remove-target` outcome replacement。多個 active rules 必須具 distinct priority；evaluation 保存套用順序與 registry 指紋，不使用 RNG，也不修改 `GameState`。

裝備合法性與 `EQUIP_ITEM` reducer 共用 `EquipmentEligibilityEvaluation`。Rules Module 以 JSON-only 條件（phase、裝備／冒險者 definition、玩家 counter 與 all/any/not）回傳穩定 rejection reason code；多條 active restriction 必須具 distinct explicit priority，否則回傳 `ORDER_POLICY_REQUIRED`。evaluation 為純函式、帶 ruleset/module fingerprint，且 Snapshot round-trip 與 lifecycle choice continuation 不重跑 reducer 或 RNG。

## 8. Command、Event 與 Choice

### 8.1 `CommandEnvelope`

- `protocolVersion`
- `gameId`
- `commandId`：唯一 ID，用於重送去重
- `actorId`
- `expectedRevision`
- `type` / `payload`

伺服器與 LocalGameSession 都重新驗證 actor、revision、phase、目標、費用與 Rules Module 限制。

玩家意圖可包含 `PLAY_ADVENTURER`、`EQUIP_ITEM`、`USE_ITEM`、`ATTACK_TARGET`、`ASSAULT_ENCOUNTER`、`BUY_CARD`、`REFRESH_MARKET`、`END_PHASE`、`RESOLVE_CHOICE` 等。英文名稱是內部 protocol，玩家畫面顯示官方中文。

### 8.2 `DomainEvent`

事件是已發生的事，至少包含：

- `eventId` / `gameId` / `revision` / `sequence`
- `type` / versioned payload
- `causedByCommandId?`
- `rulesModuleId?`
- viewer visibility metadata

核心事件包含卡片移動、抽牌、供應牌庫耗盡、目標擊敗、隊伍上限變動、結束條件觸發與計分；Rules Module 可以註冊 namespaced 事件。

### 8.3 `PendingChoice`

同一時間可有一個阻塞型 choice；它需保存來源、合法選項／selector、選取範圍、可否取消、viewer visibility 與可序列化 continuation ID。不得把 JavaScript closure 存入 state。

## 9. 可擴充的結束與計分

### 9.1 結束條件

`EndConditionRegistry` 收集所有啟用 Rules Modules 的條件。每個結果包含：

- `conditionId`
- `triggeredByEventId`
- `finishPolicyId`：例如完成當前輪次
- `priority` / simultaneous-resolution policy

基礎版註冊「所有本局魔王被擊敗」與「任一玩家完成五張羈絆」；Vol.1 註冊「究極魔神被擊敗」。engine 不用中央 boolean switch 寫死所有未來條件。

### 9.1.1 泛用羈絆條件

`BondCondition` 是 Rules Module 擁有的 versioned JSON-only 資料。它可遞迴組合 `all`、`any`、`not`，並只讀取既有玩家區域、擊敗歷史、counter、隊伍／裝備與已完成羈絆。查詢與 authoritative completion 共用同一純 evaluator；多條規則以明確 priority 作 AND 組合，同 priority 沒有排序政策即回 `ORDER_POLICY_REQUIRED`。沒有註冊條件時，舊有 `requiredBosses` fixture 是明確的相容 adapter，而非隱藏卡牌規則。

這項能力不載入任何正式或 provisional 羈絆條件；卡牌專屬獎勵與特定裝備效果仍未實作。

### 9.2 計分

`ScoringPipeline` 依序合併：

- 基礎公會內卡牌與已完成羈絆榮譽值
- Rules Module 額外分數
- 排名獎勵，例如 Vol.1 HP 第一／二／三名
- 平手與無資格 policy
- 最終勝負 tie-breakers

每一筆 `ScoreContribution` 保留 rule ID、來源、原始值與結果，方便 UI 解釋、Replay 與規則稽核。

## 10. 權威狀態與玩家投影

完整 `GameState` 只存在於 LocalGameSession、測試 host 或線上伺服器。`projectView(state, viewer)` 依 zone、card、event、counter 與 Rules Module visibility policy 產生 `PlayerView`。

hot-seat 也必須走投影流程。Vol.1 HP 標記預設只對 owner 顯示；若全體同意公開，透過正式 Command 更新 visibility policy，而不是 UI local toggle。

## 11. Snapshot、Replay 與相容性

### 11.1 `VersionedSnapshot`

保存：

- schema、engine、ruleset、protocol versions
- content pack／Rules Module manifests 與 hashes
- 完整可序列化 GameState
- RNG state、revision、最後 event sequence

Snapshot／Replay 的規則正確性只依賴 Content Pack、Rules Module 與其版本／hash。可選的 Presentation Pack ID／version 只用於重現相同視覺；缺少或不相容時以 fallback presentation 載入，不得使舊存檔失效。

### 11.2 Replay

Replay 由初始設定、精確 registry manifest、seed 與有序 Command envelopes 重建；已實作的 versioned Command Replay bundle 另保存 engine/ruleset、content hash、Rules Module config fingerprint，並可選擇精確 assertion events 與 final Snapshot。它們只作稽核，不是權威輸入；runtime 一律從 `createGame` 再走既有 `dispatch`。Events 可作快取與稽核，但不可取代相容版本資訊。

Web 的 Replay runner 只透過 `LocalGameSession` contract 取得／執行 JSON；它不讀取完整 `GameState`。若 audit assertions 不一致，engine 會回傳第一個穩定 JSON leaf divergence（path、expected、actual），session 將其投影為 UI report；runner 是唯讀操作，不改寫 live game、command log 或 local save。

### 11.3 相容性

- Snapshot migration 與 module-state migration 為具名、具版本、可測試的純函式。
- content hash 不符時不得靜默改用新卡片。
- 缺少 pack、Rules Module 或 handler 時明確回傳 incompatible error。
- Command／Event payload breaking change 必須升版本並保留 fixture。

## 12. 不變條件

1. 任一卡片 instance 同一時間只能位於一個主要 zone；配戴／附屬以明確關係表示。
2. 玩家取得的卡片 owner 不因洗牌、進隊或棄置而改變。
3. 移除遊戲的卡片不能再被抽取、購買或計分。
4. 隊伍長度不得超過當下 selector 計算出的上限；上限不是固定 5。
5. 每格最多一件裝備，除非 Rules Module／卡片明確替代此規則。
6. 每個 enemy target 只能屬於一個 encounter；部位與整體狀態不得互相矛盾。
7. `pendingChoice` 存在時，只接受對應 choice command 或規則允許的取消。
8. Snapshot 不含函式、DOM、React state、連線物件或不可序列化 RNG。
9. 所有啟用 packs/modules/handlers 存在且 hash 相符。
10. 非冪等重送的 Command，其 `expectedRevision` 必須等於權威 revision。

## 13. 衍生資料

以 selectors 計算，不重複保存：

- 當前隊伍人數上限、戰力與一般討伐的最小派遣前綴
- 各敵方 target／encounter 可否討伐
- 購買力明細、可購買卡與剩餘金錢
- 可執行 Commands
- viewer 可見資訊
- 基礎榮譽、Rules Module 分數與排名明細
- 結束條件是否滿足

衍生資料不落盤，避免卡片或 Rules Module 更新後留下過期快取。
