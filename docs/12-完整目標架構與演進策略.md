# 完整目標架構與演進策略

## 目的

本文件回答：「如何先做 MVP，但不把專案寫成只能做 MVP？」

答案是把「最終架構能力」與「目前啟用功能」分開。MVP 不啟用 AI、第一擴充或網路服務，但它從第一天就使用完整產品需要的 boundaries：純規則引擎、Content Pack、Rules Module、通用區域／敵方目標、玩家視角投影、Command/Event protocol、session adapter，以及版本化 Snapshot／Replay。

## 最終能力地圖

| 能力 | 最終 owner | MVP 如何準備 |
| --- | --- | --- |
| 核心規則 | `packages/game-engine` | 直接實作正式引擎，不放 UI 特例 |
| 基礎內容 | `packages/content-base` | 透過 ContentPack 載入 |
| 規則模式 | `RulesModule` registry | 基礎模式先走相同模組合成介面 |
| 擴充內容 | `packages/content-<pack-id>` | 基礎包先驗證相同 extension contract、替換卡與衝突檢查 |
| 遊戲區域 | `ZoneState` + zone registry | 基礎區域也用通用、具名、可序列化模型 |
| 敵方遭遇 | `EnemyEncounterState` | 基礎版可只有一個目標，但資料結構允許多目標／多部位 |
| 結束與計分 | rule registries | 基礎版條件與計分以 handler 註冊，不寫死在 phase runner |
| Web UI | `apps/web` | 只使用 PlayerView 與 GameSession |
| 本機遊戲 | local session adapter | MVP 實作，持有 authoritative state |
| 線上遊戲 | remote adapter + `apps/server` | 先共用 protocol/revision，M10 實作 transport |
| AI | `packages/game-ai` | 先提供 legal commands 與 viewer projection |
| 儲存／重連 | storage/repository adapters | MVP 先用版本化 local Snapshot、Command/Event log 與 migration contract |
| 測試工具 | `packages/test-kit` | 從 M0 建立 state builder 與 contract tests |

## 不可違反的演進規則

### 1. 不建立第二套規則

本機、AI 與伺服器都呼叫 `packages/game-engine`。不得在 server route、React component、AI policy 或 Zustand store 複製戰力、購買、phase transition 或卡牌效果。

### 2. 不讓 UI 綁死本機執行方式

feature 呼叫 `GameSession.submit()` 並接收 PlayerView。它不知道 command 是在同一個 browser 執行，還是送到遠端伺服器。只有 adapters 知道 transport 與 storage。

### 3. 基礎遊戲也當作內容包

不得先把 base cards hard-code 進 engine，之後才抽象 expansion API。第一張卡開始就使用 namespaced IDs、pack manifest、content registry 與 extension contract。

### 4. 隱藏資訊從第一版就裁切

即使 hot-seat 的 browser 記憶體持有完整 GameState，React 仍只取得目前 viewer 的 PlayerView。這能避免線上化時重寫所有 selectors 和 component props，也降低不小心顯示對手手牌的風險。

### 5. 所有操作可重送、可排序

CommandEnvelope 從 MVP 即包含 command ID 與 expected revision。local adapter 也執行去重與 revision 規則，讓斷線重連需要的語意先被測試。

### 6. 所有對局都鎖定版本

存檔與房間設定記錄 ruleset、engine schema、content pack versions/hashes 與 seed。不可只存卡片名稱，或用目前最新卡表靜默載入舊對局。

### 7. 不把基礎版數字寫成引擎常數

基礎規則模組可設定隊伍上限為 5，但引擎只讀取 `partyLimit` 的計算結果；效果或擴充可以在遊戲中改變上限。相同原則適用於起始手牌、魔王牌數、結束條件與排名獎勵。

### 8. 不把敵方建模成單一魔王欄位

以 `EnemyEncounterState` 管理一或多個 `EnemyTargetState`。基礎版遭遇通常只有一個公開魔物／魔王；究極魔神可同時存在多個獨立 HP、效果與擊破狀態的部位。不得以單一 `activeBossId` 代表所有敵方目標。

### 9. 模組狀態與區域都必須可序列化

Rules Module 可以宣告自己的具名 `moduleState`、遊戲區域與玩家計數資源。計數資源必須標示 `hidden` 或 `public`，PlayerView 依觀看者裁切；任何狀態都不得藏在 handler closure、React state 或不可重現的全域物件。

## 演進階段

### Stage A — MVP local runtime

```text
Web feature → LocalGameSession → game-engine → Snapshot + Command/Event log
                                  ▲       ▲
                             content-base  base Rules Module
```

此階段已使用 production contracts，但 runtime 全在單一 browser。

### Stage B — AI 與內容擴充

```text
ContentRegistry = content-base + selected content packs + replacements
RulesRegistry   = base module + selected expansion modules
AI actor → PlayerView → legal commands → GameSession
```

新增 packages，不更換 web feature 或 engine boundary。

### Stage C — 線上權威 runtime

```text
Web feature → RemoteGameSession → HTTP/WS → authoritative room → game-engine
                                                          ▲
                                                   approved contents
```

替換的是 session adapter 與部署位置。command、view、rules、content 與 feature UI 保持相同 contract。

### Stage D — 線上產品化

在權威 runtime 穩定後加入身份、房間邀請、持久化、觀戰、監控與部署擴縮。這些屬於 application/infrastructure，不回流污染 engine。

## 相容性策略

### Engine 與 protocol

- schema 有明確版本。
- breaking change 需 migration 或新 major version。
- server 與 client 握手時交換 protocol/content compatibility。
- typed error 使用穩定 code，顯示文字留在 client localization。

### Content packs

- manifest 宣告最低／最高相容 ruleset。
- definitions 使用永久 namespaced ID。
- pack 可宣告 dependencies 與 conflicts。
- replacement 必須由 manifest 明確宣告被替換的永久 ID；原卡與替換卡不得同時進入該局牌池。
- custom handler ID 也 namespaced；server 只執行已安裝、經核准的程式。

### Rules Modules

- 每個 module 宣告版本、相依 content packs、setup hook、事件處理器、結束條件、計分規則、額外區域與 `moduleState` schema。
- 多個模組的 handler 執行順序必須固定且可測；衝突要在開局前拒絕，不於執行中猜測。
- 基礎版只為冒險者／物資供應耗盡發布正式事件；基礎模組套用 2026-07-31 核准的專案 policy，允許這兩類公開列縮減至空而不凍結遊戲。魔物使用 3-copy cycle-anchor policy，在完整 transaction 後恆為 3 且不發布耗盡事件。第一擴充仍可監聽冒險者／物資事件令究極魔神出現；各模組行為必須明確、可重播，UI 不自行推導結果。
- module state、隱藏計數資源與多目標遭遇都要進 Snapshot、PlayerView 投影及 migration。

### Save、replay 與房間

- Snapshot 保存精確 rules modules、pack manifests/hash、module state、區域與隱藏資訊。
- migration 是具名純函式並有 fixtures。
- EventEnvelope 記錄 revision、事件 schema 版本與來源 module；不可依賴 UI 文字作為規則資料。
- 已實作 versioned deterministic Command Replay：在相同 ruleset/content 下由 initial config + Commands 重現，並可驗證 events 與最終 Snapshot。LocalGameSession 只匯出 session contract 產生的 JSON diagnostic，不把完整 `GameState` 交給 UI。
- 無法相容時明確拒絕或只讀檢視，不猜測轉換。

## 線上失敗模式預先設計

目前不用實作網路，但 contracts 必須能表達：

- `STALE_REVISION`：client 在舊狀態送出 command
- `DUPLICATE_COMMAND`：重送已處理 command，回傳原結果或最新 revision
- `NOT_AUTHORIZED`：actor 不屬於該座位
- `INVALID_COMMAND`：規則不允許
- `CONTENT_MISMATCH`：房間與 client 內容 manifest 不一致
- `RESYNC_REQUIRED`：事件序列缺口，需要重新抓 snapshot/view

把這些設為 typed errors，不在 UI 解析 server 字串。

## 擴充不應造成的修改

理想的新擴充通常只需要：

- 新 content package 與 manifest
- 新 definitions/localization/assets
- 新 Rules Module、可序列化 module state 與擴充專屬 zones
- replacement declarations、end-condition/scoring handlers
- 必要的新通用 effect primitive，或少量 namespaced handlers
- pack-specific tests
- setup/content selection UI 資料

它不應要求修改 `Game.tsx`、中央卡片 ID switch、base content 檔案或 server route 中的規則。

## 線上化不應造成的修改

理想的線上化主要新增：

- server room/application services
- remote session adapter
- transport schemas 的既有實作
- repository、identity、reconnection 與 monitoring adapters

它不應要求重寫 engine、卡牌資料、合法操作 selectors、討伐 UI 或計分。

## 架構檢查點

每個里程碑結束時回答：

1. 若明天加入一個擴充 pack，是否需要改 engine 中央 switch？
2. 若明天把 local adapter 換成 remote adapter，feature 是否需要改規則流程？
3. UI 是否接觸完整 GameState 或其他玩家隱藏資料？
4. server 是否可能信任 client 已計算的規則結果？
5. 存檔是否能辨識精確 ruleset 與內容版本？
6. AI 是否能只靠 viewer view 與 legal commands 行動？
7. 隊伍上限是否來自規則／效果計算，而非固定常數 5？
8. 敵方模型是否能同時表示多個目標與多部位究極魔神？
9. 模組狀態、擴充區域與隱藏計數是否完整進入 Snapshot／PlayerView？
10. 相同 seed + Commands 是否能重播出相同 Events 與最終狀態？

任一答案不符合目標，就先修正架構，再繼續堆疊內容。
