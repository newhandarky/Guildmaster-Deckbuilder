# 測試策略

## 測試金字塔

測試同時服務 MVP 與完整目標架構。規則案例放在 `game-engine`，內容案例放在各 content pack，session/protocol 行為用 contract suite 驗證，避免只從 web UI 測到一套本機流程。

### 純規則單元測試

數量最多、執行最快，覆蓋：

- command legality
- phase transition
- zone movement 與 ownership invariants
- party shift 與 equipment attachment
- 戰力計算、計分與 tie-breaker
- effect primitives 與個別 custom handlers
- Effect AST JSON round-trip、choice suspend/resume、seeded random replay、atomic movement failure 與 dynamic module zone
- 多 Rules Module lifecycle priority、replacement/trigger boundary、continuous evaluation boundary 與整批 transaction rollback
- pending lifecycle choice → Snapshot round-trip → `RESOLVE_EFFECT_CHOICE` → 剩餘 hooks；unknown module/hook/version 必須明確失敗
- command/event lifecycle wiring、event type filter、suspending command-before rejection，以及 event hook failure rollback command
- command-before choice continuation 的 Snapshot round-trip、單次 reducer 執行、stale/actor/option/version safety 與整批 rollback
- event-before、event-after、command-after choice 的 Snapshot round-trip 與精確 fact/boundary cursor resume
- 多 facts、同 boundary 剩餘 hooks、連續 choice、單次 reducer/facts/events/RNG 與一次 revision/event cursor commit
- post-command 後段 effect／unknown hook／registry mismatch／RNG failure 回到 command 起點；malformed、recursive 或不一致 continuation 必須拒絕
- combat modifier 正負值、跨 module priority、同 priority 拒絕、target restriction 與 defeat/remove-target replacement
- combat legal-command query 與 dispatch 必須共用 evaluation；unknown/version mismatch、stale/illegal command 不改 state 或 RNG
- CombatRewardPolicy registration、condition、priority、no-policy、defeat/remove-target、Effect AST reward execution、choice Snapshot resume、單次 policy/event/RNG 與 reward failure rollback；不載入卡牌獎勵資料
- CombatEvaluation 在 Snapshot 前後保持相同 required combat、eligibility、outcome、rule order 與 registry fingerprint
- equipment eligibility 無限制／單一拒絕／跨 module priority／同 priority `ORDER_POLICY_REQUIRED`、結構化 reason code 與 registration validation
- equipment legal-command query 與 `EQUIP_ITEM` dispatch 共用 evaluation；stale、wrong actor、registry mismatch 與非法 command 不改 state、RNG、revision 或 events
- equipment eligibility 可跨 Snapshot 重播，且與 post-command lifecycle choice suspend/resume 及 rollback 相容
- team capacity overflow policy、priority ambiguity、candidate IDs 與 dispatch rollback 必須由端到端 tests 覆蓋
- supply configuration/refill evaluation covers registered deck/row pairs, deterministic no-mutation inspection, and existing depletion handling
- refresh policy tests cover fixed row cards, policy ordering/destination, optional refill, missing policy, and effect transaction rollback
- continuous runtime tests cover source presence/expiry, explicit priority, deterministic replay, registry mismatch, and shared derived-value boundaries
- multi-target encounter tests cover policy registration/fingerprint, target/part uniqueness, health boundary, all/any completion, terminal no-repeat, attachment disposition ordering, sequence rollback, structured event payload, Snapshot restore, choice/random resume, and ATTACK_TARGET query/dispatch parity
- health-target attack resolution tests cover JSON-only policy registration/cross-reference, deterministic evaluator, legal-query/dispatch parity, partial/lethal damage, combat replacement outcome, structured facts, reward choice and post-command Snapshot resume, single revision/event cursor commit, no duplicate damage, RNG neutrality, tamper rejection, and late lifecycle rollback
- generic dice tests cover JSON-only registration, deterministic pure face evaluation, structured event payload, sequence rollback, and Snapshot-safe choice suspension without rerolling
- generic counter consent tests cover JSON-only policy registration, query/dispatch evaluator parity, request/accept/decline/cancel/explicit-expiration states, actor/game/revision/request validation, command blocking, PlayerView redaction, Snapshot tamper rejection, choice chaining, RNG stability, post-command rollback, and single revision/event-cursor commit
- lifecycle interaction dock tests cover exact-command preservation, choice grouping、copy fallback、requestId mismatch rejection、actor progress、stable terminal reason codes、private counter redaction、pending Snapshot reload、keyboard focus、mobile overflow 與 confirmation-only decline/cancel/explicit expiration
- automatic oldest/newest 與 player-choice overflow 必須驗證 evaluator、event payload、Snapshot resume 及單次 revision commit 一致
- 抽牌途中牌庫重建、供應牌庫事件與 seeded shuffle
- Rules Module state、Zone、Encounter、結束條件與 Scoring Pipeline

### 場景整合測試

以完整 `GameState` fixture 執行 Commands，驗證事件序列、module state、pending choice 與最後狀態。場景檔命名採規則意圖，例如 `combat-stops-at-first-sufficient-prefix`；英文 `combat` 可保留在程式名稱，中文描述使用「討伐」。

### UI 元件測試

確認 view model 正確呈現、合法按鈕可操作、非法目標不可提交、hot-seat 遮罩與 lifecycle interaction dock 可用。Dock 只能送出 session 提供的完整 legal Command；卡片在 pending 期間仍可 inspect，但不得藉 UI 繞過 continuation。討伐／購買 preview 只驗證 session payload 與可讀呈現，不在 React 重算戰力、費用或結果。不要在 UI 測試重複證明所有規則數學。

Accessibility suite 使用 `@axe-core/playwright` 對主牌桌、卡牌詳情、pending lifecycle 與 Replay 診斷執行 WCAG A／AA gate，並另外驗證 skip link、全域 focus-visible、卡牌具體合法動作名稱、`1280×800` 桌機 Tab／Shift+Tab／Enter／Space journey、dispatch 後焦點交接、語意化結算排名與新遠征焦點交接、確認流程焦點恢復、44px 操作目標、`320px` reflow、200% 文字放大、reduced motion 與 forced colors。Axe 通過不能取代鍵盤 journey、觸控尺寸與實際 zoom 測試。

### E2E

對應功能里程碑啟用後，至少包含：

- 建立 2 人遊戲並完成一個完整回合
- 擊敗敵人、購買卡片、休息補牌
- 儲存後 reload 恢復
- 新對局、成功保存、current v3／legacy restore 與 storage write failure 都呈現正確的 versioned persistence status；顯示 revision 必須等於 PlayerView revision，失敗寫入不得產生假的 engine error
- 桌機遠征入口驗證 fresh／restored／legacy／memory-only 摘要、JSON round-trip、繼續後 state identity、覆蓋確認的 Escape／取消焦點恢復，以及確認新遠征後 revision／events／Replay history 歸零
- 觸發兩種終局條件並完成終局輪
- 四人 hot-seat 交接不顯示下一位手牌
- 載入 Vol.1 測試 pack，觸發究極魔神、取得隱藏 HP、完成排名與終局輪

目前 M6 已有快速、固定 seed 的原創示範內容 journeys：真人透過 enabled UI 依序完成討伐與招募、休息後等待 AI 回合結束，確認 v3 local save 並 reload，接著以合法 UI control 繼續遊戲；e2e mode 的 typed、validated scenario registry 另以縮小的原創示範 pack，透過相同的 `LocalGameSession`、PlayerView、legal Commands、authoritative dispatch 與 base Rules Module，分別觸發全魔王及全羈絆終局。兩條終局 E2E 驗證 final round 不會跳過合法回合、AI 收尾後只顯示一次 scoreboard、排名／榮譽／討伐統計，以及重新開局後 revision、事件與 replay history 歸零。它不透過 `page.evaluate` 寫入 engine state，也不加入 production debug command。

所有正常 Playwright journeys 都先經過公開的遠征入口按鈕，不使用 production bypass。專屬入口案例另驗證初次建立、reload 後摘要與 continue、舊版 Replay 標示、malformed save recovery、storage failure，以及覆蓋確認在 Escape 後回到原按鈕；繼續後仍由同一組 PlayerView／legal Commands 驅動。

這些 scenario 僅驗證原創示範內容與 runtime contracts；正式基礎卡表仍未完成，且需繼續覆核卡牌名稱、數值、效果與時序。物資／魔物逐種類張數不是阻擋條件；公共供應採用 2026-07-31 核准的基礎版 policy，不是終局條件：冒險者／物資公開列可縮減至空並顯示對應訊息，3 張循環錨點則使魔物區在 committed state 始終正好 3 張。engine、Snapshot／Replay、UI 空狀態與既有 E2E regression 都必須納入驗證；其他尚未能以已確認正式資料合法啟用的終局不在本輪測試範圍。

響應式 UI 另以獨立 Playwright suite 固定驗證 `390×844` 手機直向、`844×390` 手機橫向、`768×1024` 平板直向、`1024×768` 平板橫向與 `1440×900` 桌面。每個尺寸都檢查 document 不橫向溢位、牌列自行捲動、DOM／鍵盤順序固定、卡片比例、activity rail 位置與 interaction rail 可達；詳情面板、lifecycle dock 與收合式 Replay 診斷另有跨尺寸互動驗證。

桌機 gameplay feedback 另固定驗證 `1280×720` 與 `1440×900`：五階段順序／`aria-current`、legal Commands 純衍生摘要、四種文字加形狀卡片狀態，以及 accepted action 後最新 event 只出現在單一 polite live status、較早紀錄不重複最新訊息。這些 UI assertions 不重新證明 command legality。

Action preview contract tests 驗證 schema strictness、command identity、revision、隊伍 slot／participant 基數、數值一致性與重複拒絕；engine tests 驗證一般討伐、health target damage、購買、deterministic command-before mutation、choice、counter consent、`random`／`roll-die` suppression、rollback、Snapshot round-trip、state／RNG 不變。另以 non-interference fixture 建立 PlayerView 完全相同、只差隱藏頂牌、module activation、opponent continuous source、encounter status／kind 或 reward selection 的 state，要求 legal Commands 與完整 preview payload 相同；hidden draw／zone observation、hidden combat input 與 choice 內 randomness 只可回報 requirement。Snapshot tamper case 另要求 finished no-policy encounter 在 restore 時被拒絕。Local session 與 UI 只呈現 game ID、actor、revision scope 完全相符的 preview；Playwright 確認桌機詳情顯示需求／投入／餘裕或購買前後值、未固定 lifecycle 不顯示結果、dispatch 後關閉過期詳情，以及窄螢幕仍可捲動到主要動作。

Presentation asset tests 分三層：`presentation-core` 驗證 versioned JSON manifest、路徑、variant、焦點、權利與 deterministic registry；repository script 以實際檔頭、尺寸、比例與 SHA-256 驗證所有 approved WebP，並拒絕未登錄 runtime 檔與原始 PNG／PSD；Playwright 使用 e2e-only 圖源驗證 `srcSet`、`sizes`、broken-image fallback、`63:88` 卡片比例及切換有圖／缺圖前後 revision 與 legal actions 不變。部分或零插畫覆蓋是合法產品狀態，不得誤判為 mechanics 缺失。

## Package 與 contract 測試

### Engine contract

- 相同 registry、seed、state 與 command envelope 必須得到相同結果。
- engine 不需要 DOM、browser global、React 或網路即可在 Node 執行。
- engine 不包含任何 `base:*` 或 expansion-specific import。
- 隊伍上限、敵方目標數量、結束條件與計分規則不以固定常數寫死。

### ContentPack contract

所有基礎與擴充 pack 共用測試套件：

- manifest、ruleset version、dependencies/conflicts 與 hash 合法
- namespaced definition／extension IDs 唯一
- replacement graph 正確解析，舊版與替換版不會同時進入 registry
- 每個 handler 都可序列化輸入、確定性輸出且沒有 I/O
- pack 可單獨載入，也能與宣告相容的 packs 組合

### RulesModule contract

- module state、zone state、encounter state 可通過 schema 與 JSON round-trip。
- end conditions、scoring、visibility、party-limit 與 overflow policies 使用 namespaced IDs。
- module handler 不把函式、DOM、連線或非注入式亂數寫入 state。
- Snapshot restore 後產生相同 legal Commands、PlayerViews 與衍生數值。
- lifecycle hook registration 只接受可序列化資料／Effect AST；相同 priority 回 `ORDER_POLICY_REQUIRED`，不得依陣列順序猜測。
- optional composition 必須在輸入 modules 顛倒時產生相同 canonical registry；同 priority、缺少／版本不符的 dependency、dependency order inversion、自我參照與 active conflict 都必須 fail closed。建立後修改來源 module 的 config、composition、zones、hooks 或 policies 不得改變 ruleset；重複 zone ID 或 zone owner 不符必須在建立時拒絕。composition metadata 改變但 module ID／version／config 不變時，Snapshot、Replay、legal Commands、PlayerView、scoring、party limit、preview helpers 與直接 evaluators 都必須拒絕完整 registry mismatch。
- helper setup contribution 必須驗證相同 seed 的抽樣／順序／RNG 完全一致、選入數等於本局魔王數、hidden deck 不進 PlayerView、Monster／remove-target 不輪替、Boss 恰好輪替一次、helper 08 離場時最右側超額隊員與裝備依 seat order 棄置，以及 refresh／capacity 任一步失敗時整個 command 回滾。
- helper Snapshot restore 必須提供相同 Ruleset，並拒絕 module zone kind／visibility、helper definition type、card location、lifecycle metadata 或 registry fingerprint 篡改。

### GameSession contract

local 與 remote adapters 必須共用同一套行為測試：

- submit 成功後 revision 遞增
- 重送同 command ID 不重複執行
- stale revision 回傳 typed error
- subscribe 收到順序一致的 view/events
- resume 回到最新 revision
- leave 後不再洩漏或接受該 session 的私人資料

MVP 先讓 LocalGameSession 通過；M10 的 RemoteGameSession 必須通過同一套 suite。

### PlayerView 資訊安全

- 每位玩家只能看到規則允許的手牌、選項與牌庫資訊。
- spectator view 不含任何玩家私人資訊。
- typed events 依 viewer 裁切，不在 payload 中先放完整資料再由 React 隱藏。
- hot-seat viewer 切換前後沒有上一位玩家的 cached private data。
- Vol.1 HP 預設只對 owner 顯示；全體同意公開後才出現在其他 PlayerViews／Events。

### Protocol compatibility

- command/view/event/error schemas 有 version fixtures。
- 新版能讀取宣告支援的舊 snapshot，或明確回傳 incompatible error。
- content hash/ruleset 不一致會被拒絕，不以目前最新資料繼續。
- Snapshot → restore → Replay 的 revision、RNG、module state、zones、encounters、pending choice、pending lifecycle queue 與 outer post-command cursor 一致。
- Versioned Command Replay 必須驗證 JSON round-trip、registry/config fingerprint、duplicate command ID、stale/wrong actor/game ID/illegal choice、expected events/final Snapshot assertion 與 non-finite/cyclic rejection；replay 一律重走 authoritative dispatch，不得重新選 AI、seed、choice 或 RNG。
- Counter consent 使用固定、可讀的 JSON compatibility fixtures 鎖定 request／partial accept／四種 terminal outcome、command-before／post-command／consent-to-choice cursor、structured reason、event identity、counter visibility 與 Snapshot 防竄改；暫停期間的 events 只在 `eventLogCursor` 真正提交時寫入 replay audit。
- Local save v1/v2 可恢復 Snapshot 但明確標記 replay history incomplete；v3 保存完整 accepted human/AI/choice envelopes，rejected command 不得進 log，restart 會建立新的 initial config。
- Local session persistence status 必須可 JSON round-trip；fresh → saved → restored 不改變 authoritative revision／event cursor，snapshot-only restore 保留 `replayHistoryComplete: false`，storage exception 則回報 `memory-only` 且保留 accepted in-memory state。
- Replay runner 必須驗證 malformed JSON、成功重放與 assertion divergence 的第一個 deterministic path，且 UI 執行前後的 live game 仍可操作。

## 基礎版官方 FAQ／勘誤回歸

必須建立固定 fixture：

- 使用道具後仍在玩家遊戲區域，休息才置入棄牌堆。
- 個人牌庫剩 1 張、執行抽 2：先抽 1，因仍需抽 1 才洗棄牌堆並繼續。
- 個人牌庫剩 1 張、執行抽 1：抽完後不立刻洗棄牌堆。
- 個人牌庫為空、執行抽牌：此時才洗棄牌堆；若棄牌也空則抽不到。
- 展示／查看牌庫頂時，牌庫不足或為空都不洗棄牌堆。
- 神樂的「查看」依官方勘誤改為「展示」。
- 戰力達標後不能加入更多後方冒險者。
- 討伐階段結束觸發來源已離隊時不觸發。
- `thisTurn` 進隊效果在來源離隊後仍存在。
- 巫妖的額外條件失敗不會使巫妖離場或發獎勵。
- 巴風特與基礎冒險者的不同去向。
- 奇美拉被擊敗時移除附屬魔物。
- 修爾蒂對同名他卡與自身的判定。

## Vol.1 官方規則／FAQ 回歸

- 冒險者或物資牌庫被抽空時發出供應牌庫耗盡事件並使究極魔神登場。
- 最後一隻魔王被擊敗時究極魔神登場。
- 選擇討伐究極魔神後，本回合其前後都不能討伐魔王／魔物。
- 究極魔神討伐使用整支隊伍戰力，結算後所有隊員與配戴裝備置入棄牌堆。
- 戰力超過剩餘 HP 時只取得剩餘血量標記。
- 【機械魔神】四個部位有獨立狀態；未擊敗部位的被動持續；前三個部位擊破不觸發終局，擊敗全部四部位才擊敗整體。
- 隊伍上限下降時，從最右側冒險者開始，連同裝備置入棄牌堆，直到符合上限。
- HP 標記預設不公開；只有全體同意後所有 viewers 才看得到。

## 性質與不變條件測試

適合加入 property-based testing 的性質：

- 任意成功 command 後，每個 instance 只存在於一個主要區域。
- 任意 party operation 後，隊伍長度不超過當下衍生上限，且每格裝備不超過 Rules Module 允許數量。
- 任意洗牌不增加或遺失卡片。
- 購買不會使可用資源小於 0。
- 相同初始 state 與 command 得到深度相等的結果。
- 任意 target operation 後，每個 target 只屬於一個 encounter，部位與整體擊敗狀態符合 module invariant。
- PlayerView 永遠不包含 viewer 無權看到的 counter 真值。
- Snapshot JSON round-trip 不遺失任何 module state、zone、target、visibility 或 revision。
- stale revision、非法 command 或錯誤 choice 不得執行／跳過 pending lifecycle，也不得改動 state。

## UI test snapshot 使用原則

不要把 Jest/Vitest snapshot assertion 與正式 `VersionedSnapshot` 存檔混淆。測試中不對整個 `GameState` 做大型文字 snapshot；優先精確 assertion。正式存檔則必須另外做 schema、migration 與 round-trip 測試。
