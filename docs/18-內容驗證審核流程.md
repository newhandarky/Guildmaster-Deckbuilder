# Content Verification：AI-first、例外人工確認

## 原則

本專案採 **AI-first** 內容稽核：AI 可讀取使用者合法提供、但不會提交的本機規則書與卡表視覺資料，交叉比對官方規則書、官方網站 FAQ／勘誤，建立可供 MVP 後續採用的 `provisional` 候選資料。人工只處理 `exception`，而不是逐張逐欄覆核。

此流程不改變以下邊界：候選資料不是正式 Content Pack；視覺資料絕不提交、嵌入、作為 UI 素材或進入 asset pipeline；本 PR 不載入 runtime；不清楚的資料不猜測。

## 狀態與載入門檻

| 狀態 | 意義 | 可用於 provisional MVP 研發 | 可載入正式 production Content Pack |
| --- | --- | --- | --- |
| `verified` | 有人工確認或可定位的官方文字證據。 | 是 | 仍須整包驗證與明確啟用決策 |
| `provisional` | AI 從本機視覺資料與規則／FAQ 交叉判讀；附來源定位與 confidence。 | 是，僅經明確的 provisional pack 裝配 | 否 |
| `exception` | 不清楚、衝突或會改變規則結果；需人工確認。 | 否 | 否 |
| `disabled` | 不可載入的候選／內容狀態。 | 否 | 否 |

所有目前的 `baseProvisionalContentCatalog` 候選均為 `activation: disabled`、`runtimeLoadable: false`。這防止 `base:demo` 或未來 runtime 誤把 provisional inventory 當正式基礎版內容。

## Provisional Playtest 裝配

`assembleProvisionalPlaytestPack` 是唯一可將候選轉成 Content Pack 的裝配邊界。它會先驗證整份 catalog，再逐張拒絕任何含 `exception`／`disabled`／缺少必要欄位的候選；對目前 adapter 尚未支援的效果、時序、職業、裝備限制或協助者機制，也會回傳結構化 `unsupported mechanics`，不得靜默忽略。它以中性 `placeholder:<definitionId>` 產生暫時名稱；官方名稱絕不會流入該 pack。

成功裝配的 manifest 固定使用 `contentStatus: provisional-playtest`。`createContentRegistry`／`createRuleset` 預設拒絕此狀態，呼叫端必須明確傳入 `allowProvisionalPlaytest: true`；因此它不能意外變成 production 基礎版包。起始配置可使用 legacy 的單一冒險者重複模式，或以 `partyDefinitionIds` 宣告多張不同起始冒險者；官方基礎版應使用後者。

## 每欄資料契約

每一個候選欄位必須保存：候選讀值、`status`、`confidence`、來源 ID、來源檔名、印刷頁碼或卡表區域、例外理由（如適用）。來源名稱與原始文字只屬 audit metadata；它們不會成為 Presentation Pack 顯示名稱、圖片 key 或 React UI 常數。

## AI 交叉檢查與例外分流

1. 以規則書確認卡種、設置、區域、通用時序與總張數。
2. 以卡表定位個別名稱、數值、卡面效果與可能份數。
3. 以官方網站 FAQ／勘誤覆蓋衝突或已發布修正（目前包括道具使用區、神樂、巴風特、奇美拉、修爾蒂）。
4. 一致且可讀的欄位標記為 `provisional`；官方文字／人工確認的欄位可為 `verified`。
5. 任一來源看不清、只能由總張數反推、或會影響勝負／時序的差異，標為 `exception`，列入 [基礎版 provisional 例外清單](./26-基礎版Provisional例外清單.md)。

## 例外的批次確認格式

內容負責人只需針對例外回答 `確認 A`、`採用 B`、`看不清楚` 或提供更清楚的合法頁面。每個例外需記錄決定、確認人、日期與來源定位。解決後，欄位可從 `exception` 轉為 `provisional` 或 `verified`；仍不能自動把候選載入正式 production Content Pack。

## 升格與退回

- `provisional → verified`：需人工確認或官方可定位文字；保留原始來源與決定紀錄。
- `provisional/verified → enabled`：只有在新建的正式 Content Pack 具備完整 audit、資料驗證、規則測試、dependencies/conflicts/replacements 檢查，且維護者明確啟用時才可進行。
- 任意欄位遇到矛盾或來源撤回：回退至 `exception`／`disabled`，不可沿用舊值作隱性預設。

## 素材與呈現隔離

- 不提交或顯示官方圖片、掃描、卡面、美術或商標。
- Card Definition ID 是唯一 mechanics key；名稱、圖像與短文案只能由 [Presentation Pack](./20-呈現包規格.md) 以 ID 解析。
- 即使 audit 中保存官方名稱，它也不可自動流入玩家 UI。
